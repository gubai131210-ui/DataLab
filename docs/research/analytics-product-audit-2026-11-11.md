# DataLab 数据分析、图表与交互审查（2026-11-11）

## 结论与边界

建议将 DataLab 定位为“面向制造现场的质量分析工作台”：先看到图表、关键判断和适用条件，需要时再进入完整统计结果与计算证据。现有统计领域层、结构化解释、公式代入、学习中心和报告模板都是可继续使用的基础。

目前最值得优先解决的是结果页过长、统计数值错误、工作表状态与结果来源不一致。继续增加算法和菜单之前，应完成这些链路的闭环。

本次依据当前工作区文件进行静态审查，包含已有未提交修改；起始 HEAD 为 `4f8195c`，起始分支为 `master`。MES 接口、请求、鉴权和业务逻辑不在审查范围内。未构建、未执行测试、未启动程序，也未做内存分析器或实际 DPI 截图验证。以下“确认”指能够从代码路径或解析反例确定的问题，不代表已在程序中运行复现。没有逐项认证所有算法。

统计目录现有 115 个 `.cpp` 实现文件。重点深入检查数据提取与编辑、描述统计、t 分布、正态尾概率、能力指标、回归推断、SPC 判异、时间序列绘制、结果表格、结果页、工作表切换与项目存储。高级 DOE、可靠性、多变量、机器学习等功能仍需逐模块数值认证。

## 1. 用户补充问题：图表为什么要滚动很久

### F01 / P1：长表先于图表，并按全量行数撑高页面（静态确认）

依据：`src/ui/page_renderer.cpp:162` 开始依次添加所有解释段；`:180` 添加所有统计表；`:274` 为每张表设置 `24 * (rows + 2)` 的最小高度；`:278` 添加所有诊断；`:314` 才创建图表。

一张 1000 行的结果表，单独就要求至少 24,048 像素高度。即使不需要查看逐观测计算，用户也必须经过它才能看图。`resizeRowsToContents()` 还会在创建页面时对全表进行行高计算。只增加滚动条、缩小字号或把图表简单移到顶部，都无法解决所有结果堆在同一页面的问题。

建议采用以下结果页结构：

1. 固定标题区：分析名称、来源工作表与版本、重算、导出、图表专注模式。
2. 紧凑摘要：当前方法真正需要的 3–5 个指标，显示有效 N 和关键适用条件。禁止依靠解析已经格式化的表格字符串生成摘要，应来自结构化事实或类型化指标。
3. 固定内容导航：**图表 / 统计结果 / 诊断详情 / 方法与公式**。有图的方法默认进入图表；无图的方法默认进入统计结果。
4. 图表页：I-MR 两图保持成组；Sixpack 使用有名称的组合图；其他多图提供缩略导航和单图放大。窄窗口从双列切为单列，不缩小文字硬塞。
5. 统计页：按“汇总 / 拟合与检验 / 逐观测明细”分类，默认只显示汇总；表格使用当前视口内滚动，逐观测明细按需构建，不按全量行数增加页面高度。全量 CSV/TSV 导出和复制独立于当前可见行。
6. 诊断页：首屏保留阻止分析或影响结论的告警摘要；具体规则、异常行和建议在详情页展示，不能因折叠而隐藏“结论不适用”。
7. 方法页：参数、缺失值策略、估计方法、公式代入和来源；默认折叠长推导。

重要实现边界：`page_renderer::build_page_widget()` 同时被交互工作区和报告预览使用（`src/ui/report_preview_dialog.cpp:88` 附近）。交互页面改成按需查看后，报告仍应按模板导出完整证据，不能只导出当前选中的页签。宜提取可复用的图表/表格小组件，分别由交互结果视图和报告视图编排，而不是让报告也依赖屏幕页签状态。

### F02 / P2：主工作区空间分配与分析任务不匹配（静态确认）

依据：`src/ui/mainwindow.cpp:893`、`:894` 给结果区和工作表各设最小高度 280；`:900`、`:901` 拉伸权重均为 1；`:903` 初始大小为 `{400, 380}`。左侧项目导航和右侧上下文 Dock 常驻，右侧至少 220 宽；常用工具栏在 `:598` 被隐藏。

这意味着 1080×680 等窗口中，左右 Dock 占宽、上下两块占高；结果区还要容纳分析标签、标题、卡片、表格和图表。当前配色并非唯一原因，信息层级和空间分配更直接。

建议保留工作表与结果联动能力，同时提供三种工作区：

- **数据准备**：工作表为主，数据质量和变量信息按需显示。
- **分析**：结果占主要区域，底部工作表可收起；需要核对异常点时再展开，选择图表点后定位到对应行。
- **报告**：独立预览与编辑导出内容，保留完整证据，不受分析页折叠状态影响。

左侧保留可收起的项目树；右侧上下文 Dock 默认收起，只在查看当前分析参数或编辑图表时出现，避免“全局上下文栏 + 图表内部属性面板”同时占宽。保存每种模式的布局和用户最后一次分割位置。常用动作以文字配合图标显示：导入、选择分析、重新计算、导出；完整算法目录保留在菜单/命令搜索中。

## 2. 影响计算或数据可信度的问题

### F03 / P1：t 分布分位数被限制在 ±100（静态确认）

依据：`src/domain/statistics/hypothesis_tests.cpp:147` 的 `student_t_quantile()` 在 `:152`、`:153` 固定从 `[-100,100]` 二分查找，没有扩展边界或检查目标概率是否被包围。

解析反例：两条观测 `[0,2]` 的单样本 t 均值区间，均值为 1，SE 为 1，自由度为 1。99.9% 双侧区间的临界值为约 636.619，代码无论迭代多少次都不可能超过 100。因此区间会显著偏窄。这里是数学反例推导，未执行程序。

df=1 的 t 分布为标准 Cauchy，可直接推得上述分位数；参见 [NIST t distribution](https://www.itl.nist.gov/div898/handbook/eda/section3/eda3664.htm)。该公共函数也被回归、方差分析相关区间和其他模块调用，应审计所有调用点，而不是只修单样本 t 页面。

修复方向：使用能够覆盖完整概率域的实现，或自适应扩展搜索区间、验证括界、采用稳定尾概率求逆。优先统一分布函数接口，避免各模块复制近似实现。

### F04 / P1：回归 VIF 公式使用未中心化平方和（静态确认）

依据：`src/domain/statistics/regression.cpp:561` 使用 `(X'X)^-1[j,j] * X'X[j,j]`，而该设计矩阵包含截距列。

含截距模型应使用预测变量的中心化平方和 `Σ(x_ij - x̄_j)^2` 作为乘数；等价定义为 `1/(1-R_j²)`。参见 [NIST Variance Inflation Factors](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/vif.htm)。

解析反例：只有一个非常量预测变量 `[100,101,102]` 时不存在预测变量间共线性，标准 VIF 应为 1；当前表达式得到 `30605/2 = 15302.5`，从而触发代码的 VIF>5 警告。把同一列平移为 `[-1,0,1]`，当前表达式又会得到 1。VIF 不应因为计量零点不同而变化。未执行程序。

除修正 VIF 外，回归系数虽使用 QR 求解，但推断仍重新形成并求逆 `X'X`（`:524`–`:538`），会放大尺度和近共线问题。后者属于需独立数据验证的数值风险，建议通过 QR 的 R 因子构建协方差并提供条件数/有效秩诊断，不能仅提高输出小数位。

### F05 / P1：编辑工作表没有同步单元格状态和数据契约（静态确认）

依据：`src/ui/worksheet_model.cpp:334` 的 `setData()` 修改 `rows/columns` 后直接发信号，没有同步更新 `cell_states`、`column_types`、`row_ids` 和行列元数据；`:259` 的显示逻辑却优先依赖旧 `cell_states`。`src/domain/column_extract.cpp:240` 附近的数据提取按原始文本解析。

可见后果：导入的缺失单元格原本状态为 missing，输入数值后，显示层仍显示 `*`，编辑层返回空文本，但统计提取层可能已将新数值纳入。这会造成“眼睛看到缺失，计算却使用数值”。新增行列还可能使契约长度不一致；列类型过时也影响选列向导与排序。

修复方向：将单元格修改、元数据更新和数据版本变更做成同一领域操作，覆盖粘贴、清空、删列、撤销/重做，稳定 RowId；不要每次直接重建并重编号已有行。

### F06 / P1：工作表的清洗标记、撤销历史没有完整隔离（静态确认）

依据：`src/ui/mainwindow.cpp:1470` 切换工作表时清除撤销栈，但仍使用全局 `cleaning_operations_`；`:1487` 学习中心新建演示工作表的路径既不清旧撤销栈，也没有隔离旧表的排除/隐藏标记。`TableChangeCommand`（`:219`）只持有模型指针和整表前后快照，不校验工作表身份。

风险场景：在表 A 排除若干行，再导入演示表 B，B 会继承 A 的行号标记；在 A 有编辑记录时导入 B，撤销可把 A 的快照写进 B 当前模型。切换学习中心产生的多张表时，排除标记也不会随表独立恢复。

修复方向：每张表拥有自己的清洗状态、数据版本和撤销上下文；命令携带 WorksheetId；切换激活统一经过同一入口。DOE 生成表写入当前工作表的分支也需纳入同一规则。

### F07 / P1：多工作表工作区保存时只保存活动表（静态确认）

依据：`src/ui/mainwindow.cpp:1731` 仅向 repository 传 `table_`，未传 `worksheet_registry_`；`src/infrastructure/project_repository.h` 的 save/load 接口均是单 `DataTable`；`.cpp:83`–`:87` 的表结构没有按工作表存储的数据模型。

学习中心支持在项目导航中存在多张表，但保存、重开后其他表无法恢复。`open_project()`（`src/ui/mainwindow.cpp:1331`）还没有像普通文件导入路径一样重置并重建工作表注册表，导致旧项目状态可能继续留在注册表中。

修复方向：明确项目是多工作表文档，持久化全部工作表、各表清洗状态、活动表和分析来源；版本升级需兼容现有单表项目。

### F08 / P1：旧分析图表可与当前另一张工作表发生错误联动（静态确认）

依据：`src/ui/mainwindow.cpp:795` 附近的输出行选择回调只接收行号并直接选择当前模型；`src/ui/output_workspace.cpp:245` 将当前选中行广播给所有结果图表。`OutputPage/MethodMetadata`（`src/domain/quality_types.h:2851`、`:3004` 附近）没有通用的来源 WorksheetId 和数据修订版本。

学习中心导入新表会保留旧分析输出。此时点击 A 表生成图中的点，主窗口可能选中 B 表相同行号；编辑数据后，旧结果也没有明确的过期状态。保存/导出时还可能将旧分析和当前数据源描述放在一起，应继续追查报告装配的来源字段。

修复方向：分析结果绑定 `{WorksheetId, RevisionId, RowId}`；点击图表应切换到正确来源版本，或明确提示版本已变化；旧结果保留历史意义并标记“数据已变更，待重算”。不要把不同表的第 5 行当作同一个观测。

### F09 / P1：SPC 连续同侧规则存在平方级内存与时间开销（静态确认）

依据：`src/domain/statistics/control_charts.cpp:185`–`:186`，连续同侧达到 9 点后，每来一点都重新把从 run_start 到当前点的整个区间加入向量；`:303`–`:304` 最后才排序去重。

长度 10,000 的同侧连续段会先写入 `Σ(9..10000)=50,004,964` 个索引。若 size_t 为 8 字节，仅这些元素约 400 MB（十进制，尚不计 vector 预留容量与其他结果）。这里是代码复杂度推导，未做内存实测。即便最终只有 10,000 个不同异常点，去重发生前已经承担了巨量分配和排序；erase 也不会主动缩小 capacity。

可以通过历史中心线配置形成这样的连续段。修复应使用增量标记或区间合并，让重复判异不重复保存点索引，同时保留规则触发区间和用于解释的证据。

## 3. 图表与结果交互问题

### F10 / P2：时间字符串可能被成功解析成错误时间（静态确认）

依据：`src/domain/column_extract.cpp:85`–`:109`，`sscanf()` 只需读到年月日 3 项即视为成功，未验证完整消费和日期合法性；使用 `mktime()` 自动规范化日期。

例如 `2026-11-11T08:30:00` 在 `T` 处停止，只读到日期，仍会按零点返回成功；同一天的多个 ISO 时间将重合。带时区或后缀的文本也没有严格处理；非法日期可能自动滚到另一个月。

影响链：`src/domain/graph_assembly.cpp:93` 的时间列装配调用该函数，随后图表按解析值排序。修复应明确支持格式和时区、严格验证所有字段，不能将无法识别的尾部静默忽略。

### F11 / P2：时间序列折线与点、刻度没有共用坐标变换（静态确认）

依据：`src/reporting/chart_renderer.cpp:1715` 的 `render_time_series()` 先调用 scatter 绘制点；scatter 使用 `build_scatter_plot_context()`，可应用自定义坐标范围并加入边距；`:1733` 又用数据原始极值创建 mapper 画连线，没有应用相同的自定义范围。

scatter 默认还给范围增加 5% 边距（`src/reporting/chart_plot_context.cpp:268` 附近），连线没有同样处理，因此普通自动范围下也可能点线错位；设置 X/Y 最小最大值会进一步放大问题。面积图也自行构建 mapper（`:1766`）。修复应让绘制、坐标刻度、悬停命中、框选和导出共用同一个 `ChartPlotContext`。

### F12 / P2：散点图的观测值样式设置未被完整执行（静态确认）

依据：`src/reporting/chart_renderer.cpp:515`、`:543`、`:551` 固定使用蓝色，绘制时固定圆点半径 3.5；未根据观测值 `value_style` 的 visible/color/point_style/point_size 完整绘制。其他图种也存在局部固定颜色，应逐图种核查。

这会出现属性编辑已保存，图形仍使用固定颜色/点型，深色主题与打印主题也不一致。修复应定义图种支持哪些属性；不支持的属性不显示或说明原因，支持的属性由统一绘制原语执行。

### F13 / P2：“撤销本次编辑”的基线会被自动应用覆盖（静态确认）

依据：`src/ui/graph_properties_panel.cpp:388` 的 `set_model()` 每次都执行 `original_ = model`；`:568` 附近的 `revert_changes()` 依赖 original_；而属性变更到 `src/ui/analysis_chart_widget.cpp:179` 又会把最新模型传回 `panel_->set_model()`。

因此，自动应用一次之后，“原始模型”已变成最新模型，“撤销本次编辑”无法回到进入编辑前。图表本身的撤销栈是另一条路径，不能代替这个按钮的语义。

修复方向：区分打开编辑会话时的基线、当前模型和控件刷新；刷新控件不能重置会话基线。撤销后保存、复制、PDF 与持久化结果也应一致。

### F14 / P2：统计结果表的数值排序走了字符串比较（静态确认）

依据：结果页 `src/ui/page_renderer.cpp:186` 复用 `WorksheetSortFilterProxyModel`；该代理 `src/ui/worksheet_sort_filter_proxy.cpp:60` 查询 Worksheet 的 `ColumnTypeRole`（UserRole+3），但 `ReportTableModel` 暴露的是 `ReportColumnKindRole`（UserRole+23），且只提供 DisplayRole 的格式化字符串。

因此数字列可能按 `1,10,2` 排序，小数、百分比和 `p<...` 更容易误导。完整复制/导出的顺序语义也应明确。

修复方向：为统计结果模型提供类型化 NumericSortRole，与显示文本分离；代理按数值、缺失、界限型值等规则排序。不要对任意字符串调用 toDouble 后把失败当零。

## 4. 内存、资源与性能：不要把内存增长都叫泄漏

已检查路径中，窗口/图表多采用 Qt parent 所有权，输出页关闭还调用 deleteLater（`src/ui/output_workspace.cpp:84`–`:87`、`:215`–`:217`）。这不足以证明整个程序没有泄漏，但不能仅看到 new 就判定泄漏。Qt 的子对象会随父对象销毁，参见 [Qt Object Trees & Ownership](https://doc.qt.io/qt-6/objecttrees.html)。本次未确认一项永久不可回收的堆泄漏。

已确认的资源开销如下：

- **整表撤销快照**：`src/ui/mainwindow.cpp:219`–`:257` 每条命令保留 before 和 after 两个完整 DataTable，`:344` 限制为 50 条。数量有上限，但每条大小无预算，50 条理论上可保留约 100 份表数据。一次编辑过程还产生额外临时拷贝。应改为单元格/区域增量命令，大规模结构变更再使用共享不可变快照，并设置字节预算。
- **图表撤销复制完整数据**：`src/ui/analysis_chart_widget.cpp:171` 保存完整 ChartModel，最多 32 份；修改标题、颜色也复制点、矩阵、成员行映射。建议把不可变图数据与显示属性分离，撤销只记录属性差量。
- **结果构建重复持有数据**：`src/ui/page_renderer.cpp:113` 的公式按钮捕获完整 page；`:184` 模型复制表格；`:200` 的复制回调与 `:219` 的导出回调分别捕获完整 table；`OutputWorkspace` 还保留原始 OutputPage。应使用结果仓库中的稳定身份、共享只读结果和受控生命周期，配合按需建表/建图。
- **GUI 线程计算**：`src/ui/mainwindow.cpp:2525` 同步调用 command->run；专用对话框分支也是直接调用 AnalysisService。Bootstrap、迭代拟合、矩阵和长序列分析可能阻塞交互。应引入任务执行器、进度、协作取消、输入版本快照和过期结果丢弃；仅把函数包进 QtConcurrent 不能自动获得可中断计算。参见 [Qt Concurrent Run](https://doc.qt.io/qt-6/qtconcurrentrun.html)。
- **SPC 判异平方级存储**：F09 优先级更高，不能只增加历史条数上限掩盖。

运行阶段仍需由用户验证真实泄漏：重复导入/分析/关闭结果/图表编辑/切换工作表后，对比保留对象、堆快照和句柄；区分仍被历史记录引用、分配器缓存和真正失去所有权。验收不宜只要求任务管理器内存立刻下降。

## 5. 公式审查的准确结论

### 已读实现中符合基本定义的部分

- `descriptive_statistics.cpp`：均值、样本标准差 n−1、SE、有限样本偏度/超额峰度修正的基本表达式合理；输入有有限值检查。未据此声明所有极端数据数值稳定性已通过。
- `process_capability.cpp`：所读常态能力主公式区分组内 sigma 的 Cp/Cpk 与整体 sigma 的 Pp/Ppk，Cpk 取单侧指标较小者，单侧规格不强行输出 Cp；会提示稳定性/正态性假设尚未验证。参见 [NIST capability](https://www.itl.nist.gov/div898/handbook/pmc/section1/pmc16.htm)。置信区间、不同 sigma 估计方法及非正态模型仍需分别认证。
- 缺失数据提取保留 source_rows；图表模型也包含成员行映射。这些机制应保留并完善身份与版本，不能在改 UI 时回退为重新按 0..N 编号。

### 口径差异与待验证项

- **四分位方法**：当前描述统计明确使用 `p*(n−1)` 的线性插值，与项目 `docs/statistical-methodology.md` 一致。Minitab 百分位文档使用 `p*(N+1)`。例如 `[1,2,3,4]` 的 Q1 分别是 1.75 与 1.25。两种定义不能直接互判“公式错误”；产品应标明方法，必要时提供兼容设置，箱线图/描述统计/报告使用同一口径。参见 [Minitab percentile](https://support.minitab.com/en-us/minitab/help-and-how-to/calculations-data-generation-and-matrices/calculator/calculator-functions/statistics-calculator-functions/percentile-function/)。
- **N=1 方差**：`descriptive_statistics.cpp:72` 把样本 variance 设为 0，而样本标准差保持 unavailable，统计语义不一致。应将样本方差也表达为不可计算，除非字段明确命名为总体方差。
- **极端尾概率**：`normal_distribution.cpp:13` 使用 `0.5*(1+erf())`，`:85` 上尾又做 `1-cdf`；t 双侧 p 也对接近 1 的 CDF 做相减。高 sigma 或很小 p 值会丢失有效精度，甚至显示 0。建议用 erfc/直接 survival function，明确最小可报告概率；Boost 的补概率接口说明了这一数值问题，参见 [Boost complement guidance](https://live.boost.org/doc/libs/1_65_1/libs/math/doc/html/math_toolkit/stat_tut/overview/complements.html)。不能把显示 `0.000` 解释成事件不可能。
- **回归数值稳健性**：大偏置小波动、高共线、量纲不同、近秩亏需独立验证；详见 F04。
- **认证证据**：仓库已有 ref-golden 与方法文档，但 `tests/fixtures/minitab/VALIDATION_MATRIX.md` 明确区分自建 reference 与 vendor oracle。ARIMA 的基线首行写明镜像当前候选网格。当前不能声称“全算法已与 Minitab 对齐”，也不能把已有测试文件当作本轮测试通过。

建议每种分析维护方法卡：输入要求、假设、估计方法、公式版本、输出字段、缺失策略、数值容差和验证等级。独立基准应来自手算可解数据、NIST 标准数据或另一个成熟统计实现；与 Minitab 比较时必须锁定同一方法和参数。

## 6. UI 视觉与布局建议

### 先改信息组织

第一优先是 F01/F02：图表首屏、明细独立、工作表按需展开。默认右侧数据状态无需长期占用 220 像素；来源、N、排除数可放在摘要或状态条，详细参数由“分析信息”入口展开。

每次只展示当前任务相关操作。分析设置继续沿用“变量角色 + 必要参数 + 高级选项”的渐进结构；把大量算法直接摆成按钮墙，会扩大当前不适。多分析标签需要标题、来源和状态，不应再用更多嵌套标签承载整个算法目录。

### 配色

建议浅中性色为主，降低全屏蓝灰/青色边框和卡片底色的存在感。青绿色只表示当前选择和主要操作；红色只表示异常/阻断，琥珀色表示需要检查；普通说明用中性文本，避免所有说明卡默认浅绿让人误认为通过。

可作为设计起点的色值：背景 `#F4F6F8`，内容 `#FFFFFF`，正文 `#0F172A`，次级文字 `#475569`，主操作 `#0F766E`，普通数据 `#2563EB`，警告 `#B45309`，异常 `#B91C1C`。这些是待视觉验收的建议，未声称已通过所有对比度组合。

图表数据色按分组稳定绑定；控制限与规格限采用不同线型/标签；异常同时使用点型与规则编号。黑白打印也应能区分。正文与背景对比度建议至少 4.5:1，大字至少 3:1，作为桌面可读性参考，来源为 [W3C Contrast](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)，并非声称桌面应用已获得 WCAG 认证。

### 字体、间距与适配

正文以系统中文字体与设备无关字号为基础，层级控制在标题、正文、辅助文字三档。当前 `pane_subtitle` 的 11px 辅助文字和部分 8–9pt 图例应实机检查；不要为了容纳更多表格继续缩小。

使用 8/12/16/24 的间距层级、少量结构分隔线、紧凑结果标题，避免解释卡、诊断卡、表格边框和图表边框反复套盒。统计数值右对齐、单位入列头、精度按指标配置，内部精度与展示精度分开。

用户需在 1080×680、1440×900、1920×1080 以及 100%/125%/150% 缩放下验收；重点看双图高度、表头换行、结果页导航、属性面板和导出图字号。

## 7. 做自己的特色

统计定义与可靠性应尽量遵循成熟方法，差异化放在问题组织、解释证据和制造复盘体验。Minitab 已有 Assistant 决策树、假设检查和结果解释，因此仅增加“智能选方法/自动解释”不足以构成明确差异，参见 [Minitab Assistant](https://www.minitab.com/en-us/products/minitab/assistant/)。

建议围绕以下四条完整工作流深化现有能力，均可使用普通文件数据，不依赖 MES：

1. **制造问题入口**：从“哪个设备波动更大”“改善后是否真的变好”“量具是否值得信任”“过程当前能否评估能力”进入。先检查测量系统、分组/时间结构、有效样本和适用条件，再选择分析。保留专家模式可直接选方法。
2. **图表驱动的追查**：控制图异常点 → 正确工作表与数据版本 → 对应批次/设备分层 → 残差/分布对比。一次选择贯通图、表和证据；先修复 F05–F08 再提供这一体验。
3. **改善前后对比项目**：锁定同一规格、方法、采样结构和排除策略，对比效应量、置信区间、不良率/波动变化；不能只用 p 值或 Cpk 变化宣布改善。支持保存对比快照和可复算分析配方。
4. **可信结果与学习合一**：在真实分析结果旁显示“为什么选此方法”“哪些假设尚未满足”“公式代入”“怎样解释”，复用已有 ComputationTrace 与学习中心。报告附数据版本、参数、排除原因和方法版本，让别人能复核。

第一版建议只打磨“数据体检 → 稳定性 → 能力 → 分层定位 → 改善对比 → 报告”主流程。功能目录可以很广，主工作流应更克制。
